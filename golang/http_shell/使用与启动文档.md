# http_shell 使用与启动文档

> Go 编写的 HTTP Shell 服务：`POST /` 提交命令（`cmd` / `cmd-base64` / `cmd-base64-url` / `cmd-file`），服务端用 `sh -c` 执行并逐行流式返回；固定监听 **8080** 端口，容器运行需 `-p 8080:8080` 映射。
> MCP SSE 模式（`mcp` 启动参数、`/mcp` 端点、`execute_shell` 工具）见 [MCP使用与启动文档.md](./MCP使用与启动文档.md)。

> ⚠️ 高危：无任何鉴权的任意命令执行入口，仅限可信内网/本机使用，严禁暴露公网。

## 1. 镜像说明

项目下有 4 个 Dockerfile，运行阶段基础镜像不同，决定容器内是否带 docker CLI / podman：

| Dockerfile | 基础镜像 | 容器内工具 | 适用场景 |
| --- | --- | --- | --- |
| `Dockerfile` | 默认 `scratch`（构建参数 `LATEST_FROM_BASE` 可覆盖，如 `alpine`） | 仅静态二进制 `/http-shell`，无 docker CLI（`scratch` 层内无 `sh`） | 极简服务底座/自定义基础层；需真正执行命令时用 `LATEST_FROM_BASE=alpine` |
| `Dockerfile.docker` | `adockero/http-shell:alpine` + `apk add docker-cli` | Alpine + **docker CLI** | 容器内直接执行 `docker` 命令（配合挂载 `/var/run/docker.sock` 管理宿主机容器） |
| `Dockerfile.docker.ubuntu` | `ubuntu:22.04` + `apt install docker.io`（二进制取自 `adockero/http-shell:alpine`） | Ubuntu 22.04 + **docker.io** | 需要 Ubuntu 系工具链，并在容器内执行 docker 命令 |
| `Dockerfile.podman` | `mgoltzsche/podman`（二进制取自 `adockero/http-shell`） | **podman** | 容器内执行 `podman` 命令 |

所有镜像均 `EXPOSE 8080/TCP`，`ENTRYPOINT ["/http-shell"]`，默认启动即普通 HTTP Shell 模式，`docker run` 无需覆盖参数。

### 构建命令

```bash
cd golang/http_shell

# 基础版（默认 scratch；需要 sh 执行命令时用 alpine 基础层）
docker build -t http-shell:latest .
docker build --build-arg LATEST_FROM_BASE=alpine -t http-shell:alpine .

# 带 docker-cli 版
docker build -f Dockerfile.docker -t http-shell:docker .

# 带 docker.io（Ubuntu）版
docker build -f Dockerfile.docker.ubuntu -t http-shell:docker-ubuntu .

# 带 podman 版
docker build -f Dockerfile.podman -t http-shell:podman .
```

### 启动案例

**基础版**（scratch 版能启动但容器内无 `sh`，执行命令请用 alpine 基础层的镜像）：

```bash
docker run --rm -p 8080:8080 --name http-shell http-shell:alpine
curl http://127.0.0.1:8080 --data-urlencode "cmd=echo ok"   # 返回 ok
```

**docker-cli 版**（挂载宿主机 docker.sock）：

```bash
docker run --rm -p 8080:8080 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  --name http-shell-docker http-shell:docker

curl http://127.0.0.1:8080 --data-urlencode "cmd=docker ps"
```

**docker.io（Ubuntu）版**（同样挂载 docker.sock）：

```bash
docker run --rm -p 8080:8080 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  --name http-shell-docker-ubuntu http-shell:docker-ubuntu

curl http://127.0.0.1:8080 --data-urlencode "cmd=docker version"
```

**podman 版**（挂载 docker.sock 并指定 `DOCKER_HOST`）：

```bash
docker run --rm -p 8080:8080 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e DOCKER_HOST=unix:///var/run/docker.sock \
  --name http-shell-podman http-shell:podman

curl http://127.0.0.1:8080 --data-urlencode "cmd=podman ps"
```

## 2. 参数传参案例

`POST /`，参数由 `r.FormValue` / `r.FormFile` 解析，`application/x-www-form-urlencoded`（`curl -d`）与 `multipart/form-data`（`curl -F`）均可。多个参数同时提交时按 `cmd` → `cmd-file` → `cmd-base64` → `cmd-base64-url` 顺序覆盖，最终执行最后一个非空值：

| 参数 | 提交方式 | 服务端处理 |
| --- | --- | --- |
| `cmd` | 命令原文 | 直接执行 |
| `cmd-file` | multipart 文件字段（字段名 `cmd-file`） | 文件内容整体作为命令 |
| `cmd-base64` | 标准 base64 值 | 直接 base64 解码后执行 |
| `cmd-base64-url` | URL 转义后的 base64 值 | 先 URL 解码再 base64 解码后执行 |

### 各参数 curl 案例

```bash
# 1) cmd：命令原文（含空格等特殊字符建议用 --data-urlencode）
curl http://127.0.0.1:8080 --data-urlencode "cmd=docker ps"

# 2) cmd-base64：标准 base64（值里的 + 需转成 %2B，原因见下）
curl http://127.0.0.1:8080 -d "cmd-base64=$(echo 'docker ps' | base64 -w 0 | sed 's/+/%2B/g')"

# 3) cmd-file：multipart 上传脚本文件，字段名 cmd-file，内容整体作为命令执行
printf 'echo file-start\nuname -a\ndocker ps\n' > /tmp/cmds.txt
curl http://127.0.0.1:8080 -F "cmd-file=@/tmp/cmds.txt"
```

### base64_url 特殊传参案例

```sh
# 定义函数：标准 base64 后把 + 替换成 %2B
base64_url(){
  echo "$1" | base64 -w 0 | sed 's/+/%2B/g'
}

# 生成编码值（示例命令 echo ~ 的 base64 是 ZWNobyB+Cg==，正好含 + 号）
base64_url 'echo ~'
# 输出：ZWNobyB%2BCg==

# cmd-base64-url：服务端会先做一次 URL 解码再 base64 解码，
# 用 multipart（curl -F）提交，服务端解码后 %2B 还原成 +，base64 解码正确，实际执行 echo ~
curl http://127.0.0.1:8080 -F "cmd-base64-url=$(base64_url 'echo ~')"
# 返回：/root

# 对比 cmd-base64（普通 base64，服务端不做 URL 解码）：用 -d 提交，同样要把 + 写成 %2B
curl http://127.0.0.1:8080 -d "cmd-base64=$(base64_url 'echo ~')"
# 返回：/root
```

**为什么要 `sed 's/+/%2B/g'`**：base64 字符集包含 `+`，而 HTTP 表单（`application/x-www-form-urlencoded`）规范中 `+` 表示空格，服务端解析表单时会把值里的 `+` 还原成空格，导致 base64 解码失败。先把 `+` 写成 `%2B`，表单解析后才还原为 `+`，解码才正确。

```bash
# 反例：-d 提交未转义的 +，服务端把它当空格，返回 400 base64 解码错误
curl http://127.0.0.1:8080 -d "cmd-base64=ZWNobyB+Cg=="
```

注意：`cmd-base64-url` 不要用 `-d` 提交——服务端在表单解析之外还会多做一次 URL 解码，单次 `%2B` 会被再次解码（需写成 `%252B` 双重转义才行），统一用 `-F` 提交最稳。
