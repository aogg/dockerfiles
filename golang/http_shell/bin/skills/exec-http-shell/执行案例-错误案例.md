## 案例 1：POST 后完全无输出（服务恰好在重启，命令内容无问题）

- 时间：2026-10-07 10:53 左右（Asia/Shanghai）
- 场景：上传命令文件执行 `docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"`（printf 写入，内容含转义出的真实 Tab 字符，且末尾无换行）

### 现象

- curl 返回：**完全为空**（没有任何输出、没有任何报错），表面上像"命令执行成功但没有结果"
- 紧接着 GET 探活服务返回 400（服务在线），随后重发同义命令（分隔符换成 `|`、末尾补 `\n`）立即成功

### 排查过程

1. 事后用**完全相同的字节内容**原样重发（保留 Tab、保留无末尾换行），另加两个变体（补末尾换行 / 去掉 Tab 换 `|`），三个全部 `http_code=200` 且输出正常 → **排除命令内容问题**
2. `docker inspect -f '{{.RestartCount}} {{.State.StartedAt}}' http-shell` 得到 `RestartCount=2`、`StartedAt=2026-10-07T02:53:41Z`（= 北京时间 10:53:41），正落在失败发生的时间窗口内
3. 恢复后第一次成功执行 `docker ps` 时，容器列表里 http-shell 显示 `Up 8 seconds`，印证刚刚发生过重启

### 根因

- **http-shell 容器恰好在请求时刻处于崩溃/重启窗口**（新实例 10:53:41 才起来），请求打在了已死/正在重启的实例上，连接被断开或无响应
- 客户端写法放大了问题，让"服务没回包"看起来像"命令没输出"：
  - `curl -s` 静默模式吞掉了连接层错误
  - 命令行以 `; rm -f "$CMD"` 结尾，curl 的非零退出码被 rm 的 0 覆盖，整体显示 exit 0
  - 没有打印 http_code，无法区分"服务没回包"和"服务回了空结果"

### 预防建议

1. curl 用 `-sS`（保留错误输出），并附加 `-w "\nhttp_code=%{http_code}\n"`，每次调用都能看到 HTTP 状态码
2. curl 不要和后续命令用 `;` 串联；需要判定成败时单独执行并立即 `echo curl_exit=$?`
3. 遇到空响应先做两步：GET 探活（正常应返回 400）→ **原样重发一次**；内容没问题时重发即可成功
4. 怀疑服务抖动时：
   - `docker inspect -f '{{.RestartCount}} {{.State.StartedAt}}' http-shell` 对照失败时间点
   - `docker logs --timestamps http-shell` 看当时的请求日志：有"执行的命令"日志却没有响应 → 服务端中断；连日志都没有 → 请求根本没到达实例

## 案例 2：服务端日志"标准输出读取失败: read |0: file already closed"

- 时间：2026-10-07 11:06（排查案例 1 时在 `docker logs http-shell` 中顺带发现，另一会话触发）
- 现象：服务端日志同时出现以下两行，随后仍打印 `----------执行命令---完毕-------`：
  - `标准输出读取失败: read |0: file already closed`
  - `标准错误读取失败: read |0: file already closed`
- 根因（推断）：命令进程的输出管道在服务端仍在读取时就被关闭（常见于客户端提前断开、命令进程被终止），服务端读 stdout/stderr 失败
- 提示：调用方拿到空结果或截断结果时，先查服务端日志有没有这两行；有则说明是"结果传输被中断"，不是命令本身没有输出
